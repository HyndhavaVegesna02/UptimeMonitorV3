Consolidated architecture · v3

Uptime Monitor V3

A provider-agnostic monitoring and status-page platform, redesigned from the ground up around a single organizing principle: separation by replaceability. Every decision locked across the design sessions, in one place.

Hexagonal core FastAPI · Neon · React Dynatrace → Statuspage Council-reviewed
01

Executive summary

V3 is not an incremental upgrade of the V2 MVP — it is a ground-up redesign that keeps V2's hard-won business logic (anti-flap, human-approved degradations, availability-vs-status separation) while replacing its structure with a clean hexagonal architecture. The V2 reference implementation talked to a mock publisher and a single synthetic probe; V3 consumes real multi-location synthetic results from Dynatrace and publishes to a live Statuspage.

The whole design answers one question consistently: which parts are replaceable, and which are constant? The monitored application is replaceable. The observability vendor is replaceable. The mapping configuration is replaceable. The business core — how signals become verdicts become customer-facing status — is constant, and is sealed behind a canonical boundary so that swapping any replaceable part touches it not at all.

The litmus test that governs every decision

Delete the Dynatrace adapter, write a Datadog adapter implementing the same ports, change one wiring line in the composition root — and the core does not change by a single character. If a proposed design would force a change to the core when a replaceable part is swapped, the design is wrong.

What this document covers

The canonical signal type and the boundary it enforces; the ports and adapters; how monitor identifiers map through to status-page objects; the pull-based ingestion loop with its idempotency and validation guarantees; the Neon Postgres schema; the four-stage core logic pipeline; the availability engine and its two-grain math; the proposal lifecycle with supersession and auto-obsoletion; the physical codebase structure and its CI-enforced dependency rules; the five-file API convention; the hardening resolutions from an adversarial design review, sorted into what was fixed now and what is a documented contract for later; and the deployment topology.

02

Architectural principles

Five principles recur throughout and resolve most ambiguities on their own.

P1 · Replaceability is the organizing axis

Components are sorted into replaceable (the app, the vendor, the mappings) and constant (the business core). Every structural choice is evaluated against whether it places things on the correct side of that line and keeps the line crossable in exactly one direction.

P2 · The boundary is enforced by tooling, not convention

The dependency direction (edges depend on the core, never the reverse) is checked by import-linter contracts in CI. An architectural rule that can be violated silently is not a rule. A wrong import fails the build.

P3 · The core speaks only canonical vocabulary

The core never imports a vendor type. A port signature must make sense to someone who has never heard of Dynatrace. Vendor identifiers live only inside provenance fields, never in logic.

P4 · Availability is honest; status is stable

The raw availability ratio is never smoothed — every failure drags it down truthfully. Anti-flap governs only the displayed status, never the percentage. These are two computations off the same observations, deliberately kept apart (V2's decision D-3).

P5 · Correctness beats certainty for a status page

Where freshness and responsiveness conflict, the platform reacts now and discloses uncertainty rather than waiting for perfect data — because a delayed outage announcement is worse than a disclosed-but-imperfect one. Self-correction (supersession, obsoletion) makes fast reaction safe.

03

Stack & deployment surface

The demo is a genuinely deployed system, not a local reference. The infrastructure is chosen so that the persistent pull loop has a home and the rest is serverless.

backend
FastAPI on Railway — hosts both the HTTP API and the persistent pull-loop scheduler (Vercel's serverless model can't run a long-lived loop).
frontend
React + TypeScript on Vercel — the dashboard and approval UI.
database
Neon serverless Postgres, reached through the pooled PgBouncer connection string.
observability
Dynatrace synthetic monitors; results read from Grail via DQL.
demo app
Sock Shop on Railway — the replaceable monitored application.
publish target
Statuspage — a fixed core target (not swappable in V3 scope).

Why pull-first, with push as a later option

Availability requires a complete, evenly-spaced series and a reconciliation safety net — only a pull loop guarantees that. Dynatrace exposes no native per-execution synthetic webhook; its push surface (Workflows on Davis events/problems) is better suited to enrichment than to the authoritative availability series. So pull is mandatory and authoritative; push, when added, is an optional accelerator for latency and incident seeding and flows through the same canonical ingest port — but it can never compute availability on its own.

04

The four backend zones

The backend lives under backend/src/ as four zones. The dependency direction between them is the entire architecture: every arrow points inward toward the core, and the core has no outgoing arrows.

ZoneRoleMay import
core/The constant. Domain types, port interfaces, business services.Only core itself.
adapters/The replaceable edge. Vendor and persistence concerns.core. Never another adapter.
composition/The wiring (the "main" layer). Constructs and injects.core and adapters.
api/Thin HTTP surface (FastAPI).core and composition.

Core internal layering

Within the core there is a second, finer gradient — also linter-enforced — so that drift is caught early: domain/ (pure data, depends on nothing) ← ports/ (interfaces, expressed in domain types) ← services/ (logic, calls ports, manipulates domain types). A violation can be as fine as "a domain type imported a service."

What the contracts guarantee

forbidden_modules = src.adapters, src.composition, src.api, sqlalchemy, httpx

[importlinter:contract:core-internal-layering]

[importlinter:contract:adapters-dont-cross]

Two physical conventions reinforce the separation: real Alembic migrations live at the repository top level and are versioned from day one (V2 shipped an empty versions/ and used create_all — a flagged gap); and config lives outside backend/, at the repo root, to signal that editing it is a topology change, not a code change.

05

Canonical signal

The core consumes exactly three canonical input types and never a vendor type. The spine of the system is SignalObservation — the flattened, vendor-neutral form of one synthetic monitor execution from one location.

SignalObservation — the canonical spine

signal_key
Stable name you choose — never a Dynatrace id. The shock absorber.
observed_at
UTC run time of the execution.
health
Closed enum: up · down · degraded. Not pass/fail — so a partial outage can be expressed.
source_event_id
Idempotency key for exactly-once ingestion.
source
Provenance only: {system, native_id, native_kind}. The vendor id lives here and nowhere else.
location
The probe location for this execution. Enables COUNT(DISTINCT location).
latency_ms?
Optional measured latency.
raw_ref?
Pointer to archived raw payload; the core never reads it.

The other two canonical types are ProblemSignal (enrichment / incident seed, push-era) and MaintenanceSignal (deferred). The vocabulary rule (P3) is the test: every field above makes sense to someone who has never heard of Dynatrace.

Normalization rules

  • Monitor type is provenance, not logic. HTTP, clickpath, single-browser, and NAM monitors each get their own normalizer that flattens to the same canonical shape; the type survives only as native_kind. Multi-step monitors collapse to a monitor-level verdict, with step detail archived rather than modelled.
  • Each location execution is its own observation. The adapter is deliberately dumb and lossless — it does not aggregate. Aggregation is a core concern.
  • Collapse is a core step, not an adapter step. Turning N per-location observations into one verdict per cycle happens inside the core (see §10), so the rule is provider-blind and testable.

Ports & interfaces

Ports are interfaces the core owns but does not implement. Adapters implement them. This is the inversion that lets the core depend on nothing.

PortDirectionContract
SignalIngestPortinboundThe core's front door. Adapters push batches; the port is idempotent and validating by contract (see §8). Push and pull both enter here.
StatusPublisherPortoutboundThe core sends a canonical StatusChange with a canonical component_id — never a Statuspage id. The adapter translates.
ObservationRepository
WatermarkRepository …		outboundPersistence interfaces. Neon implements them. save_new uses INSERT … ON CONFLICT DO NOTHING; the watermark is core-owned.

Why ingest is a port, not adapter logic

Because validation, idempotency, and the watermark all live on the core side of this boundary, any adapter that ever feeds the core — the Dynatrace poller now, a Datadog adapter or a push webhook later — inherits all three guarantees and cannot bypass them. The adapter's only job is to translate; the core accepts only valid canonical signals.

OOP note: the ports are abstract interfaces and the adapters are their concrete classes, constructed with their dependencies and injected by the composition root. That is the strongest object-oriented seam in the system, even though the API edge stays in the procedural five-file style (see §12).

07

Mapping ownership

A monitor result must travel from a vendor identifier all the way to a status-page object. That journey is three arrows, and signal_key sits in the middle as the stable name that absorbs vendor churn.

Option C · config owns the mapping, Neon is a read model

All three arrows live in Git-versioned config and are seeded into Neon as a read model at boot. Onboarding a new app is a reviewed commit — the right amount of friction for something that affects a customer-facing page.

  • One file per app under config/apps/ (e.g. sockshop.yaml). The app id namespaces its signal keys, and each app declares its own monitor_provider — the future Datadog seam.
  • Shared infrastructure (the Statuspage page config, the notification channel) lives in config/publishing.yaml; secrets stay in the environment.
  • Topology vs state. Mappings, signals, and components are seeded topology. Observations, proposals, maintenance, and watermarks are operational state born in Neon. Boot does a strict, fail-fast validation, then an idempotent upsert keyed on stable ids.
08

Ingest & pull loop

One pull cycle reads a per-signal watermark, queries Dynatrace for everything newer (with an overlap window for safety), normalizes each location execution, and hands the batch to the ingest port. The crash-safety guarantee comes from the strict ordering inside the port.

ingest_observations(batch):
  1. # validate each observation FIRST
     invalid → rejected_observations table   # quarantine, never silently dropped
  2. # dedupe valid ones
     INSERT … ON CONFLICT (source_event_id) DO NOTHING
  3. persist the new valid rows
  4. advance watermark to max(observed_at) over ACCEPTED observations only
  5. hand newly-inserted rows to the pipeline (collapse → anti-flap)
  # then COMMIT, then sleep
Watermark advances only after commit, only on accepted data

Overlap on read + commit-before-advance + dedupe on write = lose nothing, double-count nothing. And because the watermark moves only on accepted observations, a single malformed timestamp can never leap the cursor into the future and silently freeze ingestion (the "year-2099" failure). Validation order is validate, then dedupe, so a bad row is recorded as a rejection rather than deduped away.

The poller runs inside the Railway backend for the demo. Relocating it later (a dedicated worker, a queue consumer) is a deployment change, not a core change — the loop only calls the ingest port.

09

Neon data model

Three groups of tables. Topology is seeded from config; signals and workflow are runtime truth born in the database.

GroupTablesNature
topologyapps · signals · componentsSeeded from Git config at boot. Idempotent upsert.
signalsobservations · problem_signals · watermarks · rejected_observationsRuntime, append-only.
workflowstatus_proposals · approval_events · publications · maintenance_windowsRuntime, V2-proven shapes.

Postgres upgrades over V2's SQLite

  • timestamptz everywhere — kills the entire class of tzinfo bugs and SQLite strftime hacks.
  • JSONB for source and payloads — opaque to the core but queryable when debugging.
  • UNIQUE(source_event_id) + ON CONFLICT — concurrency-safe idempotency at the database, not a racy read-then-write.
  • Composite index on (signal_key, observed_at) for the window queries.
  • A partial unique index enforcing one active proposal per component (see §11).
  • Real Alembic migrations from day one.

Per-app behavioral config

The apps row carries per-app behavioral config (a JSONB config column, or a thin app_config keyed by app id) holding the resolved anti-flap thresholds, approval SLA, and gap policy — merged from the app's file over a global default. This is seeded topology, not runtime-mutable (Tier-2 item 6).

Modular by bounded domain — designed to grow

The schema is organized so new business-logic features can be added over time without modifying the existing core. The mechanism is the same one-directional dependency rule the code boundary uses, expressed in foreign keys: a stable spine that new feature domains attach to, never the reverse.

Two categories of addition — and only one touches the schema

A precise distinction governs what "adding a feature" means, because the two kinds have very different footprints:

calculator
Compute-only. Reads the spine, returns values, persists nothing. Lives in core/services/ and is part of the constant core — no tables, no migration, no schema footprint. Availability is a calculator: it derives availability% and completeness% from raw observations on demand and stores no result (consistent with D-1). Adding one is a pure core/services/ change.
feature module
Stateful. Reads the spine and persists its own state in its own tables, which foreign-key inward to the spine. Genuinely addable and removable. An incident module is a feature module: it tracks a lifecycle and timeline that must be remembered across cycles, so it owns an incidents table. This is the category the modularity model below governs.

The test is simply: does it persist its own state? No → calculator (no schema impact). Yes → feature module (owns inward-FK'd tables, governed by the boundary rule and its CI check). The modularity machinery exists for feature modules; calculators need none of it because they have nothing to attach.

The rules that keep it modular, all of which preserve full referential integrity (the design is add-mostly, so nothing is sacrificed for removability):

  • A new feature is new tables plus a new migration — never an ALTER to a spine table. Adding a metrics input does not touch observations; adding an incident module does not touch status_proposals. (A pure calculator adds no tables at all — it is not part of this model.)
  • Feature tables foreign-key into the spine; the spine never foreign-keys into a feature. The load-bearing rule — the spine stays unaware a feature exists, so the feature attaches (and, if ever needed, detaches) without the core caring.
  • Two sanctioned join points. New inputs reference signals (a metrics table points at signal_key the way observations does); new stateful modules reference components (and sometimes status_proposals). Every future stateful feature has one obvious correct place to connect.
  • Behavioral policy stays in config, never becomes feature tables. Anti-flap thresholds, SLA, and gap policy live in the seeded app_config JSONB, added and removed by editing Git-versioned YAML — modular at the config layer, not as runtime toggle-tables.
  • Strong foreign keys throughout. Within the spine and from features into the spine, with ON DELETE behavior chosen explicitly per relationship. Integrity is upgraded over V2, not weakened.
The boundary is enforced, not just documented (P2 applied to the schema)

The one-way FK rule above must be a rule, not a convention — the same standard the code boundary is held to. So a CI check reads the database's actual foreign keys from the information schema and fails the build if any spine table references a feature table. A developer who adds a column to components pointing at incidents breaks the build, exactly as a forbidden import would. This closes the asymmetry where the code boundary was tool-enforced but the schema boundary was honor-system.

# test_schema_boundary.py — runs in CI against a migrated test DB
SPINE = {"apps", "signals", "components", "observations", "watermarks",
         "rejected_observations", "problem_signals", "status_proposals",
         "approval_events", "publications", "maintenance_windows"}

# Query information_schema for every FK whose source table is in SPINE
# and whose target table is NOT in SPINE → that is an outward reference.
violations = [fk for fk in all_foreign_keys()
              if fk.source_table in SPINE and fk.target_table not in SPINE]

assert not violations, f"Spine references a feature table: {violations}"

The spine list is the explicit allowlist of constant-core tables; everything else is a feature domain. The check is direction-only — features referencing the spine inward is correct and passes; the spine referencing outward is the violation.

What this does and does not give you

You get clean modularity at the feature-domain boundary: a whole incident module or metrics pipeline can be added (or dropped) without disturbing the constant core, because the dependency is one-way. You deliberately do not get table-level removability inside the spine — the proposal lifecycle and its approval events are cohesive by design. Wanting to remove a spine table would signal the core thesis changed, which is a redesign, not a migration.

Gone from V2 — and why

No transactions / transaction_steps / component_targets tables, and no verdict table. Verdicts are derived from observations on read (V2's decision D-1), so storing them would be a denormalized cache inviting drift. The canonical observation is the single source of truth; everything else is computed.

10

Core logic pipeline

The constant core, expressed as four pure stages. Nothing here mentions Dynatrace, Grail, DQL, or executions — the pipeline consumes canonical observations and produces canonical proposals, and would not change if the vendor were swapped. This is the litmus test applied to the brain.

Stage by stage

1 collapse
Per cycle: all-up → up, all-down → down, some-down → degraded. Maintenance is checked here and excluded from the verdict (it counts as planned work, not up or down — V2's FR-8); a maintenance cycle short-circuits the rest of the pipeline. Multi-step monitors collapse internally.
2 streak
Count consecutive verdicts of the same health, reading backward, over non-maintenance verdicts only. Governs the displayed status, never the availability ratio (P4 / D-3).
3 anti-flap
Pure lookup from streak length to status, driven by per-app config: ≥5 failing → major, ≥3 → partial, ≥2 → degraded, a single failure → internal warning (logged, never published), ≥2 passes → operational. A sustained degraded streak maps to degraded-performance. Thresholds resolve via component → app → that app's block.
4 decide
Compare proposed status to the component's current published status. Same → nothing. Worse → a degradation proposal (the human-approval gate). Better → a recovery (auto-publishes). This stage also reconciles open proposals and computes the per-component skew flag (Tier-2 item 7).
Lineage

Collapse is the one genuinely new stage (V2 had single-location checks). Streak, the anti-flap thresholds, severity-ordered direction, dedup, and the availability-vs-status separation are all V2 logic re-expressed on canonical types. V3 re-houses the brain behind a clean boundary and adds the one stage multi-location monitoring demands.

11

Availability engine

The availability engine is the system's first calculator — compute-only, no tables, part of the constant core (core/services/availability.py). It reads observations through the repository port and computes two percentages on demand, persisting nothing (D-1). It runs in parallel to the four-stage pipeline and never consults the streak (P4).

Two metrics, two grains

The engine computes two numbers from the same observation stream but at deliberately different grains — they answer different questions and must never share a denominator.

MetricGrainFormula
Availability %collapsed verdicts (cycles)passing ÷ (total − maintenance) — up passes; down/degraded don't; maintenance excluded both sides; gaps excluded from the denominator (default exclude policy).
Completeness %raw observationsactual ÷ (intervals × distinct_locations) where intervals = window ÷ interval and locations are COUNT(DISTINCT location).
The grain split is correct, not inconsistent

Availability asks "what fraction of cycles were healthy" — a cycle is the unit a status page cares about. Completeness asks "did all expected location-runs report" — the honesty check on the data feeding availability. The location-aware completeness denominator is the multi-location fix: V2 computed expected = window ÷ interval for a single probe; multiplying by distinct locations stops a 3-location signal reporting 300% completeness. The location field on the canonical observation is what makes COUNT(DISTINCT location) possible.

Group rollup

A group's availability and completeness are each the min of its children — a group is only as available as its worst component. Counts (verdicts, passing, maintenance, gaps) sum across children; percentages take the min. Children with no data are excluded from the min but their absence stays visible. (V2-proven, preserved.)

Skew, surfaced

Because the engine already reads watermarks, it also surfaces the per-component skew flag (item 7): a feeding signal lagging its peers by more than its own interval. This rides alongside completeness — related but distinct, since completeness can be low for other reasons — and appears both on the dashboard and as an annotation on any proposal born during skew.

Read strategy — derive now, measure, optimize only if needed

Pure-derive, with a designed-in escape hatch

The engine recomputes from raw observations on every read — no stored verdicts, honoring "derive everything" (D-1). The one unquantified risk is 30-day multi-location reads under dashboard auto-refresh (a 5-min × 3-location × 30-day window scans tens of thousands of rows per signal per request). Rather than optimize speculatively, the entry points are shaped so a short-TTL (~60s, matching the refresh interval) cache drops in cleanly if measurement shows it's needed. The cache would be ephemeral and self-invalidating — still derived, never persisted verdicts — so it doesn't reintroduce the cache-drift problem that storing verdicts would. Build pure, point a realistic dataset at it, measure, and add the cache only if the numbers demand it.

Shape

@dataclass(frozen=True)
class AvailabilityResult:
    availability_pct: float | None    # over verdicts
    completeness_pct: float | None    # over observations
    total_verdicts: int
    passing_verdicts: int
    maintenance_verdicts: int
    gap_verdicts: int
    distinct_locations: int           # makes the completeness denominator auditable
    window: str
    computed_at: datetime

Provider-blind by construction: it consumes canonical observations and would not change if Dynatrace became Datadog. Pure functions, fully unit-testable with in-memory observations — the same approach that gave V2 its ~130 tests. All SQL lives behind the repository port, not smeared into the service (fixing a V2 leak).

12

Proposal lifecycle

A proposal is not a frozen artifact waiting for a human — it is valid only while it still matches what the engine currently computes. Every ingest cycle reconciles open proposals against current reality. This single rule covers escalation, de-escalation, and recovery-before-approval, and it closes a real V2 bug.

The reconciliation rule

Each cycle, the engine compares its freshly computed status against any open proposal for the component:

  • Worse computed → the pending lesser proposal moves to superseded; a new proposal for the worse status becomes the single active decision. The human always sees one proposal per component — the current worst.
  • Recovered → the pending degradation moves to obsoleted with an audit reason, and nothing is published. The component was never shown down to customers, so there is nothing to clear. This honors the approval gate by suppressing a now-false alarm rather than publishing without approval.
  • Same → leave it.
The constraint that makes it concurrency-safe

A partial unique index enforces one active proposal per component_id (over the actionable states). Supersession means there is only ever one active proposal per component anyway, so the index needs no to_status dimension. A losing concurrent writer hits ON CONFLICT DO NOTHING and no-ops with a debug log — silent correctness plus a signal for whether multi-instance polling ever actually collides.

The bug this fixes: in V2, a pending degradation could be approved after the outage had already recovered, publishing a "Major Outage" for an incident that was over. Auto-obsoletion makes that impossible.

Five-file API convention

Every FastAPI feature at the edge uses the same five files as Hyndhava's existing module convention, so any developer who knows the existing codebase recognizes every module. The one adjustment: the edge service.py stays thin and delegates inward.

backend/src/api/v1/<feature>/
├── __init__.py        # package marker (+ optional router re-export)
├── controller.py      # routes, scopes, rate limits, status codes
├── models.py          # pydantic HTTP DTOs only
├── validation.py      # HTTP-input shape checks only
└── service.py         # THIN: validate → call core → shape result
FileHoldsMay import
controller.pyHTTP wiring. No logic.models, validation, service
models.pyRequest/response DTOs the client sees. Not canonical domain types.pydantic only
validation.pySyntactic input checks. Business validation lives in core.stdlib only — no services
service.pyOrchestration: validate, call a core service via the container, shape the HTTP result.core, container — never another feature
The adjustment that lets both styles coexist

The convention governs the edge's shape; the boundary governs where logic lives. The edge service.py orchestrates and shapes — it never holds business logic and never imports another feature's service. The real logic (collapse, anti-flap, availability) lives in core/services/, provider-blind, and never imports FastAPI.

  • No horizontal feature imports. If a feature needs another's data, it goes through a core service — not from api.v1.other.service import …. This eliminates the in-function import hack the existing convention uses to dodge circular imports, and is enforceable as a fourth linter contract.
  • Two "service" words, two layers. The edge service.py (orchestration) and core/services/* (logic) share the word but live in different packages; the import path always says which you're looking at.
14

Hardening · Tier 1

An adversarial design review (four reviewer lenses — distributed systems, security, future-maintainer, SRE-skeptic — plus a chairman synthesis) found that the architecture was sound but several seams between separately-designed topics were unwelded. Tier 1 are the correctness and safety holes, all resolved.

T1.1 · Transaction boundary vs side effects

Commit the database first, then make notification and publication calls in a try/except — never hold a transaction open across a webhook. A failed notification is logged; the proposal already exists, and the human reliably finds out through two independent channels: the dashboard always shows pending proposals, and an SLA re-notify job retries. delivery: best-effort

T1.2 · Concurrent duplicate proposals

A partial unique index enforces one active proposal per component; supersession + auto-obsoletion handle "the world changed while pending" (see §11). On collision, ON CONFLICT DO NOTHING + debug log. This also fixed the stale-approval bug. supersession model

T1.3 · Canonical validation gate

Validation lives on the core ingest port, as the first act of ingestion — so push inherits it and cannot bypass it. Invalid observations are quarantined to a real rejected_observations table; the rest of the batch proceeds (no poison pill); and the watermark advances on accepted observations only (kills the year-2099 poisoning). reject-and-quarantine

T1.4 · Authentication — deliberately deferred

No API auth in v1, by choice. actor stays self-declared and is therefore not a trustworthy audit field until auth lands. Recorded as a known pre-production gap: this must be closed before exposing a real customer-facing Statuspage outside a demo. When added it is edge-only — a require_scope dependency on the controllers plus a token-derived actor — touching no core, ports, adapters, or schema. The hexagonal boundary is what makes deferring it low-regret. close before production

15

Hardening · Tier 2

Decisions that touch the schema or core logic — settled now because they are cheap before code and expensive after.

T2.5 · Multi-location completeness

The gap formula is location-aware: expected = (window ÷ interval) × distinct_locations_observed. Observed-distinct means zero config maintenance and self-adjustment as locations change. Known limit: it cannot detect a single location going fully silent (it catches whole-monitor death) — upgrading to a declared location set is additive, recorded for later. Availability is measured per verdict; completeness per observation — different grains, intentionally.

T2.6 · Per-app vs global config

Behavioral policy (anti-flap thresholds, approval SLA, gap policy) is per-app with global defaults; infrastructure (Statuspage page, notification channel) stays global. Config is seeded topology, not runtime-mutable. Per-app notification routing is a recorded later enhancement. Anti-flap thresholds resolve via component → app → block.

T2.7 · Components with multi-watermark signals

React-now-and-disclose. Component status is computed each cycle on whatever verdicts are present — never waiting at the speed of the slowest signal. Safe because anti-flap filters transient skew and supersession/obsoletion self-corrects premature reactions. A skew flag fires when a feeding signal lags its peers by more than its own interval (self-scaling, no hardcoded number) and surfaces in two places: a dashboard indicator, and an annotation on any proposal born during skew — so the approver sees the caveat at the gate.

Deployment topology

Five pieces in three categories, mapping exactly to the replaceability thesis: a constant platform, a replaceable monitored app, and external SaaS we configure but don't host. The one structural fact that shapes everything: the pull loop is a persistent process, so the backend cannot be serverless.

Sock Shop is a separate Railway service precisely because it is the replaceable monitored app — it could be deleted and Dynatrace pointed at something else without touching platform deployment. The two SaaS pieces are external dependencies, configured but not hosted by us.

Statuspage is called a fixed target yet sits behind StatusPublisherPort — a deliberate asymmetry with the Dynatrace adapter. The Dynatrace adapter exists for genuine replaceability (the litmus test swaps it for Datadog). The publisher port exists for testability — a mock publisher in tests, the real one in production — not because a second real publisher is anticipated. Same pattern, two different justifications, both intentional.

Deploy flow — migrations as a separate gate

This is your B decision made concrete. Schema authority lives in the deploy pipeline, not the application — the app assumes a correct schema and uses it. A failed migration halts the deploy and leaves the old container serving (fail-safe), rather than crash-looping a live container (fail-messy). It is also instance-model-independent: the migration runs exactly once as a deploy step regardless of how many app instances run.

The boundary is logical, not physical

The core, the pull loop, the scheduler, the seeder, and the API all run co-resident in one Railway container. The hexagonal boundary is enforced at the import level by CI contracts, not at the process level — this is not microservices. Swapping Dynatrace for Datadog does not redeploy a different core; it ships a new adapter inside the same container and changes one wiring line. The constant core is a module that cannot be illegally imported, not an independently deployable service.

Runtime wiring

Data flow matches the architecture: Dynatrace runs synthetic checks against Sock Shop; the backend pulls results from Dynatrace (never querying Sock Shop directly — it is monitored, not queried); the backend computes and pushes approved status to Statuspage. The frontend talks only to the backend API.

Connection split & secrets

Neon exposes two connection strings used for two purposes: the direct (non-pooled) string for the migration release step (DDL misbehaves through PgBouncer's transaction pooling), and the pooled string for all app runtime. All secrets live in Railway env, never in YAML; config files reference env var names, never values.

Two surfaces, not one

The system presents two distinct surfaces to two audiences. The internal dashboard (React SPA on Vercel) is the operator cockpit — live health, availability, pending proposals with approve/reject, check history, maintenance, publications. The public Statuspage (Statuspage SaaS) is what customers see — only the final, approved, published statuses. The approval gate sits between them: a degradation appears as a proposal on the dashboard, a human approves it, and only then does it reach the public page. The dashboard carries forward V2's six-tab information architecture (Dashboard · Availability · Approvals · Check History · Maintenance · Publications), visually redesigned, and deploys independently on Vercel — a UI redesign is a frontend-only deploy that never touches the backend, schema, or API contract. Unlike V2's mock publisher, V3's Statuspage is real, which is what makes the deferred auth a live exposure.

The demo path — making it watchable

The pipeline only visibly acts when a monitored service fails, so the demo needs a controllable failure. The failure shim (primary) is a toggle-able proxy in front of the one Sock Shop route the headline monitor watches — instant, precise, scriptable. Stopping the Sock Shop Railway service is the authentic-outage variant. The catch is two latency gates: clicking "break" → Dynatrace's next synthetic run detects it → the backend's next pull cycle ingests it. So the demo environment runs tight cadences (≈1-minute monitors, short poll interval) to keep click-to-react near two minutes rather than ten, and the operator narrates the expected delay.

Single instance, safe by design on redeploy

One backend instance is the intent; the idempotency built into ingestion (unique source_event_id, watermark commit-before-advance, the partial unique proposal index) is the safety net if a deploy overlap briefly runs two. Railway replaces the container on redeploy; the watermark persists in Neon, so a restart mid-poll resumes losing nothing — the pull loop simply pauses for the swap (tens of seconds, invisible at a 1-minute cadence).

The auth exposure is now live

With the backend on a public Railway URL and auth deferred, the decision endpoints are reachable by anyone who finds the URL — CORS restriction stops browser cross-origin calls but not direct API calls. This is the accepted posture for a short-lived, unadvertised demo. The moment it becomes longer-lived or customer-visible, auth is the first addition — edge-only, slotting into the controllers without touching core, ports, adapters, or schema.

Bottom line

The architecture held under adversarial review — no reviewer broke the canonical boundary, the dependency direction, or the swap-ability premise. What the review found were unwelded seams between topics designed in different sessions, and every one is now welded or carries a documented contract. Several resolutions (auto-obsoletion, react-and-disclose) improved on the initial recommendations. The design is tightly coupled in the good sense: the pieces compose, the edge cases have decisions, and the enhancement paths are isolated so they stay additive. It is ready to build.
