## Facts (verified against code)
- The five-file API convention (dossier §13) divides each endpoint feature directory (e.g. `api/v1/decisions/`, `api/v1/components/`, `api/v1/approvals/`, `api/v1/maintenance/`, `api/v1/availability/`, `api/v1/history/`, `api/v1/publications/`, `api/v1/topology/`, `api/v1/sample_mode/`) into exactly five modules:
  - `__init__.py`: Router re-export only (`api/v1/decisions/__init__.py`, `api/v1/components/__init__.py`, `api/v1/approvals/__init__.py`, `api/v1/maintenance/__init__.py`, `api/v1/availability/__init__.py`, `api/v1/history/__init__.py`, `api/v1/publications/__init__.py`, `api/v1/topology/__init__.py`).
  - `controller.py`: Exposes HTTP routes, parameters, and status codes with no business logic (`api/v1/decisions/controller.py::create_decision`, `api/v1/components/controller.py::list_components`, `api/v1/approvals/controller.py::list_open_proposals`, `api/v1/maintenance/controller.py::list_maintenance_windows`, `api/v1/maintenance/controller.py::schedule_maintenance_window`, `api/v1/availability/controller.py::get_availability`, `api/v1/availability/controller.py::get_component_availability`, `api/v1/history/controller.py::get_history`, `api/v1/publications/controller.py::list_publications`, `api/v1/topology/controller.py::get_topology`).
  - `models.py`: Defines Pydantic DTOs for HTTP input and output, keeping domain models encapsulated (`api/v1/decisions/models.py::DecisionRequest`, `api/v1/components/models.py::ComponentDTO`, `api/v1/approvals/models.py::ProposalDTO`, `api/v1/maintenance/models.py::MaintenanceWindowDTO`, `api/v1/maintenance/models.py::CreateMaintenanceRequest`, `api/v1/availability/models.py::AvailabilityDTO`, `api/v1/availability/models.py::SignalAvailabilityDTO`, `api/v1/availability/models.py::ComponentAvailabilityDTO`, `api/v1/history/models.py::ObservationDTO`, `api/v1/publications/models.py::PublicationDTO`, `api/v1/topology/models.py::ComponentTopologyDTO`, `api/v1/topology/models.py::TopologySignalDTO`).
  - `validation.py`: Performs syntactic checks using the Python standard library only, raising structured validation errors (`api/v1/decisions/validation.py::validate_decision_request`, `api/v1/components/validation.py`, `api/v1/approvals/validation.py`, `api/v1/maintenance/validation.py::validate_maintenance_request`, `api/v1/availability/validation.py::validate_availability_request`, `api/v1/availability/validation.py::validate_component_availability_request`, `api/v1/history/validation.py::validate_history_request`, `api/v1/publications/validation.py` — no-op for the GET endpoint, `api/v1/topology/validation.py` — no-op for the GET endpoint).
  - `service.py`: Performs the thin orchestration layer by validating input, resolving core services via dependencies, and shaping the DTO response (`api/v1/decisions/service.py::DecisionService.record_decision`, `api/v1/components/service.py::ComponentsService.get_all_components`, `api/v1/approvals/service.py::ApprovalsService.get_open_proposals`, `api/v1/maintenance/service.py::MaintenanceService.list_windows`, `api/v1/maintenance/service.py::MaintenanceService.create_window`, `api/v1/availability/service.py::AvailabilityService.get_availability`, `api/v1/availability/service.py::AvailabilityService.get_component_availability`, `api/v1/history/service.py::HistoryService.get_history`, `api/v1/publications/service.py::PublicationsService.list_recent`, `api/v1/topology/service.py::TopologyService.get_topology`).
- The `api-feature-independence` contract in `pyproject.toml` prevents horizontal features from importing each other (currently forbids imports between `src.api.v1.decisions`, `src.api.v1.health`, `src.api.v1.components`, `src.api.v1.approvals`, `src.api.v1.maintenance`, `src.api.v1.availability`, `src.api.v1.history`, `src.api.v1.publications`, `src.api.v1.topology`, and `src.api.v1.sample_mode`).
- The feature's FastAPI DI provider (`service.py::get_decision_service`, `service.py::get_components_service`, `service.py::get_approvals_service`, `service.py::get_maintenance_service`, `service.py::get_availability_service`, `service.py::get_history_service`, `service.py::get_publications_service`, `service.py::get_topology_service`) lives in the feature's own `service.py` (which may import the container), so `controller.py` imports ONLY this feature's `models` + `service` — no core type leaks into the controller (AC1).
- The FastAPI application factory in `composition/app.py::create_app` wires adapters, clocks, and services into the application state for dependency injection. As of STORY-014c, `observation_repo` is wired into `app.state` (default: `PostgresObservationRepository(engine)`) and retrieved via `src/api/dependencies.py::get_observation_repo`. The `get_clock` dependency was added to `src/api/dependencies.py` simultaneously.
- STORY-045 (approve→publish→write-back, dossier §12/§17): `core/services/approval.py::ApprovalService` gains a REQUIRED keyword-only `publisher: StatusPublisherPort` constructor param (`approval.py::ApprovalService.__init__`) — deliberately not optional/defaulted, since a silently-unwired publisher was the exact defect this story closes. `approve()` (`approval.py::ApprovalService.approve`) publishes a `StatusChange(component_id, to_status)` AFTER `_decide` has resolved the proposal and recorded the approval event (commit-first); `reject()` publishes nothing. `create_app` (`composition/app.py::create_app`) gains a symmetric `publisher: StatusPublisherPort | None = None` param: when `None`, it defaults to `composition/publish_helper.py::build_publisher` (see [[statuspage-publish]]) wired against whatever `component_repo`/`publication_repo` this call resolved — the REAL Postgres path always has both, so production always gets the full D2 chain — or a bare `LoggingPublisher` when either repo is absent (an injected-fakes test exercising proposal-only endpoints is not obligated to supply both). `create_app` reads the optional Statuspage creds via `composition/settings.py::load_statuspage_secrets` (NOT `load_live_secrets`, which requires the unrelated DYNATRACE_* vars) and `Config.statuspage_mapping()`. Every existing `ApprovalService(...)` construction in `backend/tests/test_approval.py` was rewritten (not deleted) for the new required kwarg (2026-06-29 contract-change agreement); `backend/tests/test_decisions.py` gained `test_decision_endpoint_approve_publishes_and_writes_back_status`, composing the real `StatusWritebackPublisher`+`RecordingPublisher` chain with fakes and injecting it via `create_app`'s `publisher=` override, proving an HTTP approve records a publication AND writes `components.status` back (visible via `GET /api/v1/components`).
- The `maintenance` feature (STORY-036) provides:
  - `GET /maintenance` (`api/v1/maintenance/controller.py::list_maintenance_windows`) — returns all scheduled maintenance windows as `list[MaintenanceWindowDTO]`.
  - `POST /maintenance` (`api/v1/maintenance/controller.py::schedule_maintenance_window`) — schedules a new maintenance window; returns `MaintenanceWindowDTO` with HTTP 201. Syntactic validation is performed by `api/v1/maintenance/validation.py::validate_maintenance_request` (stdlib only); domain invariant (`ends_at > starts_at`) is enforced by the `MaintenanceWindow` domain model itself.
- The `availability` feature (STORY-014c; STORY-044 D4/D5, sprint-30) provides:
  - `GET /availability` (`api/v1/availability/controller.py::get_availability`) — returns per-signal `AvailabilityDTO` computed by `AvailabilityCalculator.compute` (dossier §11). `signal_key` is required (422 if missing). `since`/`until` default to the last 24h via the injected clock (window resolution factored into the shared `service.py::_resolve_window` helper, also used by the component endpoint). `interval_seconds` (STORY-044 AC3/D5, audit finding H2): when the caller supplies a positive value it wins outright with NO topology lookup (back-compat: an unknown signal_key with an explicit interval keeps the historical degenerate all-None 200); when omitted, the signal's configured interval is read from the seeded topology via `SignalRepository` — an unknown signal_key on this default path raises `SignalNotFoundError` (404, a CONTRACT CHANGE from the old silent 60s-default behavior — see [[canonical-types-and-ports]]), a seeded-but-unconfigured signal raises `SignalIntervalUnconfiguredError` (409). The 60s stopgap default and the stale "STORY-040 will supply" comment are GONE. No-data window → `availability_pct=None`/`completeness_pct=None` (not 500).
  - `GET /availability/component/{component_id}` (`api/v1/availability/controller.py::get_component_availability`, STORY-044 AC2/D4) — returns `ComponentAvailabilityDTO{component_id, rollup: AvailabilityDTO, signals: list[SignalAvailabilityDTO]}`: one `AvailabilityCalculator.compute` per child signal mapped to `component_id` (each with ITS OWN configured interval from the seeded topology — no interval query param on this endpoint), rolled up via `core/services/availability.py::rollup_group` (see [[core-pipeline-and-availability]]). Unknown component id → 404 (`ComponentNotFoundError`); naive since/until → 422 (2026-06-28 agreement); a child with `interval_seconds IS NULL` → 409 (`SignalIntervalUnconfiguredError`, unreachable once fully seeded); a zero-signal component → 200 with `signals: []` and the `rollup_group([])` degenerate (never a 500); a no-data window surfaces null percentages, never a 500. `AvailabilityService` (`service.py::AvailabilityService.__init__`) gained REQUIRED `component_repo: ComponentRepository` + `signal_repo: SignalRepository` ctor deps (contract change — `get_availability_service` resolves them via the existing `get_component_repo` + new `get_signal_repo` providers; every construction/provider call site was rewritten, 2026-06-29 agreement).
- The `history` feature (STORY-014c) provides:
  - `GET /history` (`api/v1/history/controller.py::get_history`) — returns per-signal observation DTOs (`list[ObservationDTO]`, most-recent first) via `ObservationRepository.in_window`. Empty window → 200 + `[]`. `ObservationDTO` omits `source`/`raw_ref`/`source_event_id` (client-facing subset of `SignalObservation`).
- The `topology` feature (STORY-044 D3/AC1, sprint-30) provides:
  - `GET /topology` (`api/v1/topology/controller.py::get_topology`) — returns `list[ComponentTopologyDTO]`, one entry per component from `ComponentRepository.list_components()` (that order), each `{id, name, signals: list[TopologySignalDTO]}` with signals grouped from `SignalRepository.list_signals()` by `component_id` and sorted by `signal_key`. `TopologySignalDTO = {signal_key, name, interval_seconds, component_id}` — `interval_seconds` is `None` when the seeded row predates the D1 backfill. Empty topology → 200 `[]`; a component with zero mapped signals → `signals: []`; an orphan signal (`component_id IS NULL`) appears NOWHERE in the nesting (AC1 is component-centric). No query params. Sourced from the seeded topology via `ComponentRepository`/`SignalRepository` — never re-reads `config/` at request time (proven by a DB-gated end-to-end test seeding through `composition/seed.py::seed_topology`). `signal_repo` param added to `create_app` (symmetric with `component_repo`: real branch builds `PostgresSignalRepository(engine)` when `None`; injected branch leaves as-passed), `app.state.signal_repo`, `get_signal_repo` added to `api/dependencies.py`, router registered in `api/v1/__init__.py`.
- The `sample_mode` feature (STORY-048 D3, sprint-31, a TEMPORARY feature — see [[sample-mode]])

  `topology/validation.py`'s pattern). `sample_mode_repo: SampleModeRepository | None = None` added

  `PostgresSampleModeRepository(engine)`), `app.state.sample_mode_repo`,
  `get_sample_mode_repo` added to `api/dependencies.py`, router registered in `api/v1/__init__.py`,
  `src.api.v1.sample_mode` added to the `api-feature-independence` contract. This whole feature —

- The `publications` feature (STORY-037) provides:
  - `GET /publications` (`api/v1/publications/controller.py::list_publications`) — returns recent `PublicationDTO` records most-recent-first via `PublicationsService.list_recent`. Empty repo → 200 + `[]`. `PublicationDTO` (`api/v1/publications/models.py::PublicationDTO`) has fields: `id`, `component_id`, `status` (string), `published_at`, `proposal_id` — distinct from the `Publication` domain type. `publication_repo` is wired into `create_app` + `app.state` (default: `PostgresPublicationRepository(engine)`); `get_publication_repo` added to `src/api/dependencies.py`. `src.api.v1.publications` added to the `api-feature-independence` contract in `pyproject.toml` (lint-imports: 5 kept / 0 broken).
