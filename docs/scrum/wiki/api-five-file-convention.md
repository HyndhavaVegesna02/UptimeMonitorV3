## Facts (verified against code)
- The five-file API convention (dossier §13) divides each endpoint feature directory (e.g. `api/v1/decisions/`, `api/v1/components/`, `api/v1/approvals/`, `api/v1/maintenance/`, `api/v1/availability/`, `api/v1/history/`, `api/v1/publications/`) into exactly five modules:
  - `__init__.py`: Router re-export only (`api/v1/decisions/__init__.py`, `api/v1/components/__init__.py`, `api/v1/approvals/__init__.py`, `api/v1/maintenance/__init__.py`, `api/v1/availability/__init__.py`, `api/v1/history/__init__.py`, `api/v1/publications/__init__.py`).
  - `controller.py`: Exposes HTTP routes, parameters, and status codes with no business logic (`api/v1/decisions/controller.py::create_decision`, `api/v1/components/controller.py::list_components`, `api/v1/approvals/controller.py::list_open_proposals`, `api/v1/maintenance/controller.py::list_maintenance_windows`, `api/v1/maintenance/controller.py::schedule_maintenance_window`, `api/v1/availability/controller.py::get_availability`, `api/v1/history/controller.py::get_history`, `api/v1/publications/controller.py::list_publications`).
  - `models.py`: Defines Pydantic DTOs for HTTP input and output, keeping domain models encapsulated (`api/v1/decisions/models.py::DecisionRequest`, `api/v1/components/models.py::ComponentDTO`, `api/v1/approvals/models.py::ProposalDTO`, `api/v1/maintenance/models.py::MaintenanceWindowDTO`, `api/v1/maintenance/models.py::CreateMaintenanceRequest`, `api/v1/availability/models.py::AvailabilityDTO`, `api/v1/history/models.py::ObservationDTO`, `api/v1/publications/models.py::PublicationDTO`).
  - `validation.py`: Performs syntactic checks using the Python standard library only, raising structured validation errors (`api/v1/decisions/validation.py::validate_decision_request`, `api/v1/components/validation.py`, `api/v1/approvals/validation.py`, `api/v1/maintenance/validation.py::validate_maintenance_request`, `api/v1/availability/validation.py::validate_availability_request`, `api/v1/history/validation.py::validate_history_request`, `api/v1/publications/validation.py` — no-op for the GET endpoint).
  - `service.py`: Performs the thin orchestration layer by validating input, resolving core services via dependencies, and shaping the DTO response (`api/v1/decisions/service.py::DecisionService.record_decision`, `api/v1/components/service.py::ComponentsService.get_all_components`, `api/v1/approvals/service.py::ApprovalsService.get_open_proposals`, `api/v1/maintenance/service.py::MaintenanceService.list_windows`, `api/v1/maintenance/service.py::MaintenanceService.create_window`, `api/v1/availability/service.py::AvailabilityService.get_availability`, `api/v1/history/service.py::HistoryService.get_history`, `api/v1/publications/service.py::PublicationsService.list_recent`).
- The `api-feature-independence` contract in `pyproject.toml` prevents horizontal features from importing each other (currently forbids imports between `src.api.v1.decisions`, `src.api.v1.health`, `src.api.v1.components`, `src.api.v1.approvals`, `src.api.v1.maintenance`, `src.api.v1.availability`, `src.api.v1.history`, and `src.api.v1.publications`).
- The feature's FastAPI DI provider (`service.py::get_decision_service`, `service.py::get_components_service`, `service.py::get_approvals_service`, `service.py::get_maintenance_service`, `service.py::get_availability_service`, `service.py::get_history_service`, `service.py::get_publications_service`) lives in the feature's own `service.py` (which may import the container), so `controller.py` imports ONLY this feature's `models` + `service` — no core type leaks into the controller (AC1).
- The FastAPI application factory in `composition/app.py::create_app` wires adapters, clocks, and services into the application state for dependency injection. As of STORY-014c, `observation_repo` is wired into `app.state` (default: `PostgresObservationRepository(engine)`) and retrieved via `src/api/dependencies.py::get_observation_repo`. The `get_clock` dependency was added to `src/api/dependencies.py` simultaneously.
- The `maintenance` feature (STORY-036) provides:
  - `GET /maintenance` (`api/v1/maintenance/controller.py::list_maintenance_windows`) — returns all scheduled maintenance windows as `list[MaintenanceWindowDTO]`.
  - `POST /maintenance` (`api/v1/maintenance/controller.py::schedule_maintenance_window`) — schedules a new maintenance window; returns `MaintenanceWindowDTO` with HTTP 201. Syntactic validation is performed by `api/v1/maintenance/validation.py::validate_maintenance_request` (stdlib only); domain invariant (`ends_at > starts_at`) is enforced by the `MaintenanceWindow` domain model itself.
- The `availability` feature (STORY-014c) provides:
  - `GET /availability` (`api/v1/availability/controller.py::get_availability`) — returns per-signal `AvailabilityDTO` computed by `AvailabilityCalculator.compute` (dossier §11). `signal_key` is required (422 if missing). `since`/`until` default to the last 24h via the injected clock. `interval_seconds` defaults to 60 (stopgap until STORY-040 supplies per-signal config). No-data window → `availability_pct=None`/`completeness_pct=None` (not 500).
- The `history` feature (STORY-014c) provides:
  - `GET /history` (`api/v1/history/controller.py::get_history`) — returns per-signal observation DTOs (`list[ObservationDTO]`, most-recent first) via `ObservationRepository.in_window`. Empty window → 200 + `[]`. `ObservationDTO` omits `source`/`raw_ref`/`source_event_id` (client-facing subset of `SignalObservation`).
- The `publications` feature (STORY-037) provides:
  - `GET /publications` (`api/v1/publications/controller.py::list_publications`) — returns recent `PublicationDTO` records most-recent-first via `PublicationsService.list_recent`. Empty repo → 200 + `[]`. `PublicationDTO` (`api/v1/publications/models.py::PublicationDTO`) has fields: `id`, `component_id`, `status` (string), `published_at`, `proposal_id` — distinct from the `Publication` domain type. `publication_repo` is wired into `create_app` + `app.state` (default: `PostgresPublicationRepository(engine)`); `get_publication_repo` added to `src/api/dependencies.py`. `src.api.v1.publications` added to the `api-feature-independence` contract in `pyproject.toml` (lint-imports: 5 kept / 0 broken).
