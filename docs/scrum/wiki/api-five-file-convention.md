## Facts (verified against code)
- **The five-file SHAPE is a standing test, not a convention to be remembered.** Each feature
  asserts set equality on `{__init__, controller, models, validation, service}.py` for its own
  directory — pattern:
  `backend/tests/test_publications_endpoint.py::test_publications_module_five_file_shape`. Seven
  features carry one as of STORY-155b (was eight before that story removed the `sample_mode`
  feature and its own five-file-shape test); the live count is
  `grep -rc "def test_.*_module_five_file_shape" backend/tests/` rather than a number written
  here, because a number here would drift and the grep cannot. A new feature ships its own shape
  test in the same story (`.scrum/checklists/implementer.md`). So a missing or extra file fails
  `pytest` — but set equality cannot see whether business logic leaked into `controller.py`, so
  the ROLES below are the half that can still drift silently and are written out for that reason.
- The five-file API convention (dossier §13) divides each endpoint feature directory (e.g. `api/v1/decisions/`, `api/v1/components/`, `api/v1/approvals/`, `api/v1/maintenance/`, `api/v1/availability/`, `api/v1/history/`, `api/v1/publications/`, `api/v1/topology/`) into exactly five modules:
  - `__init__.py`: Router re-export only (`api/v1/decisions/__init__.py`, `api/v1/components/__init__.py`, `api/v1/approvals/__init__.py`, `api/v1/maintenance/__init__.py`, `api/v1/availability/__init__.py`, `api/v1/history/__init__.py`, `api/v1/publications/__init__.py`, `api/v1/topology/__init__.py`).
  - `controller.py`: Exposes HTTP routes, parameters, and status codes with no business logic (`api/v1/decisions/controller.py::create_decision`, `api/v1/components/controller.py::list_components`, `api/v1/approvals/controller.py::list_open_proposals`, `api/v1/maintenance/controller.py::list_maintenance_windows`, `api/v1/maintenance/controller.py::schedule_maintenance_window`, `api/v1/availability/controller.py::get_availability`, `api/v1/availability/controller.py::get_component_availability`, `api/v1/history/controller.py::get_history`, `api/v1/publications/controller.py::list_publications`, `api/v1/topology/controller.py::get_topology`).
  - `models.py`: Defines Pydantic DTOs for HTTP input and output, keeping domain models encapsulated (`api/v1/decisions/models.py::DecisionRequest`, `api/v1/components/models.py::ComponentDTO`, `api/v1/approvals/models.py::ProposalDTO`, `api/v1/maintenance/models.py::MaintenanceWindowDTO`, `api/v1/maintenance/models.py::CreateMaintenanceRequest`, `api/v1/availability/models.py::AvailabilityDTO`, `api/v1/availability/models.py::SignalAvailabilityDTO`, `api/v1/availability/models.py::ComponentAvailabilityDTO`, `api/v1/history/models.py::ObservationDTO`, `api/v1/publications/models.py::PublicationDTO`, `api/v1/topology/models.py::ComponentTopologyDTO`, `api/v1/topology/models.py::TopologySignalDTO`).
  - `validation.py`: Performs syntactic checks using the Python standard library only, raising structured validation errors (`api/v1/decisions/validation.py::validate_decision_request`, `api/v1/components/validation.py`, `api/v1/approvals/validation.py`, `api/v1/maintenance/validation.py::validate_maintenance_request`, `api/v1/availability/validation.py::validate_availability_request`, `api/v1/availability/validation.py::validate_component_availability_request`, `api/v1/history/validation.py::validate_history_request`, `api/v1/publications/validation.py` — no-op for the GET endpoint, `api/v1/topology/validation.py` — no-op for the GET endpoint).
  - `service.py`: Performs the thin orchestration layer by validating input, resolving core services via dependencies, and shaping the DTO response (`api/v1/decisions/service.py::DecisionService.record_decision`, `api/v1/components/service.py::ComponentsService.get_all_components`, `api/v1/approvals/service.py::ApprovalsService.get_open_proposals`, `api/v1/maintenance/service.py::MaintenanceService.list_windows`, `api/v1/maintenance/service.py::MaintenanceService.create_window`, `api/v1/availability/service.py::AvailabilityService.get_availability`, `api/v1/availability/service.py::AvailabilityService.get_component_availability`, `api/v1/history/service.py::HistoryService.get_history`, `api/v1/publications/service.py::PublicationsService.list_recent`, `api/v1/topology/service.py::TopologyService.get_topology`).
- **The shared edge infrastructure (`_shared/` package)** (dossier §13, §17; Proposal §6.2) houses cross-feature HTTP policies. It is underscore-prefixed to explicitly denote it is not a feature (excluded from `api-feature-independence` and the five-file structure test). It contains:
  - `errors.py`: The ONE exception-to-HTTP-status mapping registry — a `_STATUS_BY_EXCEPTION: dict[type[Exception], int]` dict-driven registry (STORY-075 review fix, replacing seven copy-pasted per-exception closures) plus a single `_make_handler(status_code)` factory, installed as FastAPI exception handlers via `install_error_handlers(app)` (`api/v1/_shared/errors.py::install_error_handlers`). Body stays `{"detail": str(e)}` and HTTP statuses are identical to keep the error contract frozen. Feature controllers and services let domain exceptions propagate rather than mapping them locally. The registry maps: `SyntacticValidationError`→422, `SignalNotFoundError`/`ComponentNotFoundError`/`ProposalNotFoundError`→404, `SignalIntervalUnconfiguredError`/`ProposalNotOpenError`→409, `MaintenanceWindowNotFoundError`→404. There is deliberately NO base `ValueError`→422 catch-all (STORY-075 removed it): that used to mask genuine server-side `ValueError`s — and internal `pydantic.ValidationError`, which subclasses `ValueError` — as 422s instead of letting them surface as 500s (proven by `test_shared_errors.py::test_shared_errors_bare_value_error_500`).
  - `validation.py`: Defines the ONE shared `SyntacticValidationError(ValueError)` (STORY-075 review fix) — hoisted here because `_shared/errors.py` needs a syntactic-validation exception type to map to 422, but `_shared` may never import a feature package (`api/v1/_shared/validation.py::SyntacticValidationError`). Each feature's own `validation.py` (`availability`, `decisions`, `history`, `maintenance`) imports and re-exports this same class instead of defining its own copy-pasted subclass — `feature.validation.SyntacticValidationError` still resolves for back-compat, and no raise site or message changed.
  - `windowing.py`: The single home for read-window defaulting policy (24h constant + `resolve_window` function) consumed by the availability and history services, preventing duplication and quiet disagreements between features (`api/v1/_shared/windowing.py::resolve_window`).
  - `middleware.py`: Documented empty seam (STORY-181, sprint-63) — its docstring states no CORS middleware is required (dev: Vite proxy; prod: same-origin behind CloudFront, STORY-089) and remains a seam for future middleware such as authentication, currently unassigned (`api/v1/_shared/middleware.py`).
  - It is fenced by the `api-shared-no-feature-imports` contract which forbids `src.api.v1._shared` from importing any feature package (`pyproject.toml` ("api-shared-no-feature-imports")) — `_shared/validation.py` defining `SyntacticValidationError` and features importing FROM `_shared` is the allowed direction; `_shared` importing a feature is still forbidden and unbroken (`lint-imports`: 9 kept / 0 broken as of STORY-206 sprint-69's ninth contract; the `api-shared-no-feature-imports` CONTRACT this Fact is about is itself unchanged by STORY-206 — the count moved because a DIFFERENT, unrelated contract was added elsewhere).
- The `api-feature-independence` contract in `pyproject.toml` prevents horizontal features from importing each other (currently forbids imports between `src.api.v1.decisions`, `src.api.v1.health`, `src.api.v1.components`, `src.api.v1.approvals`, `src.api.v1.maintenance`, `src.api.v1.availability`, `src.api.v1.history`, `src.api.v1.publications`, and `src.api.v1.topology`).

- The `maintenance` feature (STORY-036) provides:
  - `GET /maintenance` (`api/v1/maintenance/controller.py::list_maintenance_windows`) — returns all scheduled maintenance windows as `list[MaintenanceWindowDTO]`.
  - `POST /maintenance` (`api/v1/maintenance/controller.py::schedule_maintenance_window`) — schedules a new maintenance window; returns `MaintenanceWindowDTO` with HTTP 201. Syntactic validation is performed by `api/v1/maintenance/validation.py::validate_maintenance_request`: non-empty `component_id`, tz-aware `starts_at`/`ends_at`, (STORY-075, sprint-42) both timestamps in UTC (`utcoffset() == timedelta(0)`, else a clean `SyntacticValidationError("starts_at must be in UTC.")`/`"ends_at must be in UTC."`), and (STORY-052, sprint-37) `ends_at` strictly after `starts_at` — moved here from the domain layer so the 422 for that case returns a clean one-line `SyntacticValidationError` message instead of `service.py`'s domain-`ValueError` path rendering the raw multi-line Pydantic `ValidationError` blob. The STORY-075 UTC-offset check closes the same gap for a tz-aware-but-non-UTC timestamp (e.g. `+05:30`): previously it passed this syntactic layer and only got caught by the domain `MaintenanceWindow` field validators, whose `pydantic.ValidationError` used to be caught by `_shared/errors.py`'s now-removed base `ValueError`→422 handler — without the syntactic check it would have become a 500. The domain model's own UTC and `ends_at > starts_at` invariants (`core/domain/maintenance.py::MaintenanceWindow._require_starts_at_utc`, `_require_ends_at_utc`, `_require_ends_after_starts`) stay as defense in depth and are now unreachable via the HTTP path for these specific cases.
  - `DELETE /maintenance/{window_id}` (`api/v1/maintenance/controller.py::delete_maintenance_window`, STORY-065, sprint-45) — deletes a scheduled maintenance window. Unknown ID raises `MaintenanceWindowNotFoundError` (mapped to 404 in `errors.py`). `CreateMaintenanceRequest` and `MaintenanceWindowDTO` gained an optional `title: str | None = None` field.
- The `availability` feature (STORY-014c; STORY-044 D4/D5, sprint-30) provides:
  - `GET /availability` (`api/v1/availability/controller.py::get_availability`) — returns per-signal `AvailabilityDTO` computed by `AvailabilityCalculator.compute` (dossier §11). `signal_key` is required (422 if missing). `since`/`until` default to the last 24h via the injected clock (window resolution factored into the shared `service.py::_resolve_window` helper, also used by the component endpoint). `interval_seconds` (STORY-044 AC3/D5, audit finding H2): when the caller supplies a positive value it wins outright with NO topology lookup (back-compat: an unknown signal_key with an explicit interval keeps the historical degenerate all-None 200); when omitted, the signal's configured interval is read from the seeded topology via `SignalRepository` — an unknown signal_key on this default path raises `SignalNotFoundError` (404, a CONTRACT CHANGE from the old silent 60s-default behavior — see [[canonical-types-and-ports]]), a seeded-but-unconfigured signal raises `SignalIntervalUnconfiguredError` (409). The 60s stopgap default and the stale "STORY-040 will supply" comment are GONE. No-data window → `availability_pct=None`/`completeness_pct=None` (not 500).
  - `GET /availability/component/{component_id}` (`api/v1/availability/controller.py::get_component_availability`, STORY-044 AC2/D4) — returns `ComponentAvailabilityDTO{component_id, rollup: AvailabilityDTO, signals: list[SignalAvailabilityDTO]}`: one `AvailabilityCalculator.compute` per child signal mapped to `component_id` (each with ITS OWN configured interval from the seeded topology — no interval query param on this endpoint), rolled up via `core/queries/availability.py::rollup_group` (see [[core-pipeline-and-availability]]). Unknown component id → 404 (`ComponentNotFoundError`); naive since/until → 422 (2026-06-28 agreement); a child with `interval_seconds IS NULL` → 409 (`SignalIntervalUnconfiguredError`, unreachable once fully seeded); a zero-signal component → 200 with `signals: []` and the `rollup_group([])` degenerate (never a 500); a no-data window surfaces null percentages, never a 500. `AvailabilityService` (`service.py::AvailabilityService.__init__`) gained REQUIRED `component_repo: ComponentRepository` + `signal_repo: SignalRepository` ctor deps (contract change — `get_availability_service` resolves them via the existing `get_component_repo` + new `get_signal_repo` providers; every construction/provider call site was rewritten, 2026-06-29 agreement).
- The `history` feature (STORY-014c; STORY-064 added `response_status_code`/`check_type`; STORY-094 added `limit`) provides:
  - `GET /history` (`api/v1/history/controller.py::get_history`) — returns per-signal observation DTOs (`list[ObservationDTO]`, most-recent first) via `ObservationRepository.in_window`. Empty window → 200 + `[]`. `ObservationDTO` omits `source`/`raw_ref`/`source_event_id` (client-facing subset of `SignalObservation`); it now ALSO carries `response_status_code: int | None` (mapped from `SignalObservation.response_status_code`) and `check_type: str` (mapped from the persisted `source.native_kind` — always present, since `Provenance` is mandatory) via `HistoryService.get_history`'s DTO mapping (`api/v1/history/service.py::HistoryService.get_history`). Absent `limit` → unchanged full-window behavior; `limit=0`/negative/non-int → 422 (declarative `ge=1` + FastAPI's own int coercion, no new `validation.py` code needed). The frontend (`client.ts::getHistory`) deliberately does not send `limit` — see [[frontend-zone]].
